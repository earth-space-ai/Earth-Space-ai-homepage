1. Motivation

Why benchmark AI on Earth System Model development?

ESMs are large Fortran/C systems where a small code edit can change long-horizon climate behavior.

  • Development work mixes scientific reasoning, legacy HPC code, and physical constraints.
  • Tasks include bug fixing, parameter changes, scheme switching, and process edits.
  • A model can compile and still be scientifically wrong.
Central Question

Can an AI agent produce code that is not just executable, but physically valid: conserving mass, respecting bounds, and improving agreement with observations?

2. Benchmark Gap

Existing coding benchmarks miss the failure mode we care about

Language gap

Most benchmarks are Python-first. ESM work is dominated by Fortran 90/2008 and C.

Physics gap

Passing tests is not enough if the patch breaks conservation laws or parameter bounds.

Validation gap

Real scientific changes must be judged against observations, not only unit or regression tests.

Target failure mode: code that runs but is physically wrong.

5. Construction Pipeline

How tasks are built

01

Mine commits

Scan public git history for physics-relevant Fortran/C changes.

02

Classify commits

Use keyword filters plus Gemini classification into PBF, PO, PSS, PRM, or discard.

03

Generate task fields

Create description, scientific background, and physical constraints.

04

Freeze ground truth

Store the parent source snapshot and real developer diff for evaluation.

All source commits are dated before 2023-10-01.

7. Evaluation

Dual-correctness scoring separates “runs” from “is scientifically right”

Computational correctness

  • Build success
  • Runtime completion
  • Regression checks
  • Valid output artifacts

Physical correctness

  • Conservation laws hold
  • Physical bounds respected
  • Agreement with observational targets improves
  • Primary metrics: Pass@k and PhysViolation rate
Main point: build success and physical validity should be reported separately.
